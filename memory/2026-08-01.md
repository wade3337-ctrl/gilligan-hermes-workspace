### 🐛 FIXED: mic "access denied" was OpenJarvis's OWN Permissions-Policy header (not Windows/Chrome)
- Symptom: Jason's Chrome showed "Microphone access denied" even though Windows mic privacy was fully On
  (Chrome listed under "let desktop apps access mic", last-used 7/31), the Chrome site permission was
  Allow (blue toggle), mic works in Telegram, laptop w/ working mic. TEXT chat worked perfectly
  ("Yep, it's me—Gilligan, running on GPT-5.6 Sol through Hermes Agent").
- **Root cause:** OpenJarvis's server security middleware sends `permissions-policy:
  camera=(), microphone=(), geolocation=()` on EVERY response — `microphone=()` = empty allowlist =
  the page's own origin may NOT use the mic. Browser kills getUserMedia BEFORE OS/site perms matter.
  And `hooks/useSpeech.ts` catches ANY getUserMedia error and mislabels it "Microphone access denied"
  (misleading — it's a Permissions-Policy block, not a permission denial). Ironic: ships a mic feature,
  header forbids the mic.
- **Verify the real cause with `curl -sI` and read the Permissions-Policy header** — that's what nailed it
  after 3 layers of user-side settings all checked out. Lesson: when a web app says "mic denied" but OS +
  browser + site all allow, suspect the SERVER's Permissions-Policy header, not the user.
- **Fix:** `~/.openjarvis/src/src/openjarvis/server/middleware.py` — changed BOTH the live header and the
  `SECURITY_HEADERS` constant to `camera=(self), microphone=(self), geolocation=()`. Backup
  `middleware.py.bak-premicfix-*`. Restarted `openjarvis-serve.service`; header now `microphone=(self)`,
  verified via curl (local + tailnet). ⚠️ This patch is in the OpenJarvis SOURCE — `jarvis self-update`
  / `git pull` would revert it; re-apply after any OpenJarvis update.
- User needs a HARD reload (Ctrl+Shift+R) to drop the cached old header, then mic works.
