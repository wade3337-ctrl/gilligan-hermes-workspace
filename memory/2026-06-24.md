- **Root cause:** `Evaluate$CompanyYears` builds CompanyYears = one row per distinct `ProjectYears.StartDate` across
  all the company's projects (deduped only on identical StartDate) → Anaheim's multi-calendar projects (Mar–Feb +
  Sep–Aug + Jan–Dec) make overlapping same-label rows. `GenerateContractPeriod`'s `CROSS APPLY ORDER BY April-pref,
  lowest CompanyYearID` then picks the **empty** Sep–Aug row (89816) over the live Mar–Feb (90020) on regeneration.
- **Fix (proc, ORDER BY only):** prefer the company-year whose window **contains the project-year start**
  (`ProjectYears.StartDate + 1 BETWEEN cy.StartDate AND cy.EndDate` — TrimIT's own idiom); April-pref + ID kept as
  fallbacks → single-same-label-row companies 100% unchanged. GLM vetoed a naive exact-match (would orphan
  April-start cities); window-containment avoids that.
- **GOTCHA (Skipper asked):** the bug is in **TWO procs** — the bulk driver `CURSOR$GenerateContractPeriods` has its
  own inlined copy (enumerates periods from the wrong CY). Both fixed + proven. Also: `GSTSBACKUP` DB on same server
  has a stale 2014 copy (deploy to GSTS only); `CURSOR$GenerateContractPeriods$dev` (2015, dead); trigger
  `ContractYearScopesPostInsert` is an auto-regen path (covered by worker fix). Dual-webroot `.cfm` shadow N/A (DB fix).
