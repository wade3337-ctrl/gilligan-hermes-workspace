🌳 AI-Assisted V1 Cleanup Plan

The in-house alternative to the $300K+ "V2 migration." Goal: make V1 (TRIM IT) secure, reliable, and AI-accessible — the V1.5 foundation. Security first.

How it works — safety IS the point

Roles: Gilligan (Claude) drafts & reviews every change and verifies the result · Codex executes server-side · you approve · a trusted "hands" runs prod changes.
The rules (already how we work on TRIM IT):
  • Backup-first, always — timestamped .bak before any change; nothing is ever deleted.
  • PLAY first, then PROD — test every change on the play sandbox (nightly restore of prod), verify, then apply to production.
  • One change at a time, numbered batches, rollback chain on each.
  • Gilligan never touches the production database directly — changes are drafted, reviewed, approved, then run.
This is the same discipline that reconciled the customer-verifier and the daily monitor to the penny.

The work, prioritized

Phase 1 — Security DO NOW

  • SQL-injection sweep & fix — AI scans the whole codebase (~3,600 stored procs + the .cfm/.cfc pages) for unparameterized queries, then wraps them safely (cfqueryparam). This is the exact risk Travis flagged — and the thing he implied costs "hundreds of thousands." It doesn't.
  • Kill the sa database login — the app currently connects to SQL Server with full god-rights. Replace with a least-privilege account (only the permissions the app needs). Hours of work, huge risk reduction.
  • Fix plaintext passwords — migrate the stored passwords to hashed + salted, with a safe transition path.
  • Baseline hardening — suppress detailed error leakage, tighten session/cookie handling, add input validation on the exposed forms.

Phase 2 — Reliability & data hygiene NEXT

  • Retire the ~200 zDelete-*/backup tables (GBs) — after dependency checks, on a copy first.
  • Add missing enforced foreign keys, incrementally, to stop bad data at the source.
  • Fix broken screens (the data-driven menu / ObjectPath↔.cfm mismatches).
  • Targeted data-quality cleanup (the kind the customer-verifier surfaced).

Phase 3 — AI-accessibility — lay Arbor's rails THEN

  • Expand secure read-only endpoints (like the MonitorData.ReadOnly.cfm we already built) so Arbor agents read clean data.
  • Document the data model for AI consumption.
  • This is where V1.5 cleanup literally becomes the Arbor backend — same work, double duty.

Honest caveats (so this is real, not a sales pitch)

  • It needs "hands." AI drafts and verifies, but a trusted person must run prod changes with judgment. Today that's you running Codex prompts — for sustained pace you may want a part-time ColdFusion-literate person (still a fraction of $40K/mo).
  • SQLi scope is unknown until the sweep runs — could be a focused set or broad across the 3,600 procs. The scan tells us; then we size it accurately.
  • Prod changes are never zero-risk — mitigated hard by PLAY-first + backups + one-at-a-time, but discipline is required.
